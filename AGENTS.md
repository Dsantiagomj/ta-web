# Agent contract for ta-web

Rules for any agent that changes this repo. It is the new torrentearcano.com: Torre's Dofus quest guides, achievements, classes, Dofus guides and checklists, with member accounts, per-member progress and premium features. It replaces the Squarespace site and the embeds served from `silvestre-checklist`. The plan, decisions and phases are in `docs/legacy/plan.md`; visual rules are in `DESIGN.md`.

The app skeleton exists: Next.js with Payload, the design tokens, the test suites, the git hooks and CI. Most of the rest is **planned**. When a rule names a path or command that does not exist yet, create it that way. How to run it locally is in the Development section of `README.md`.

## When this applies

Every change: code, content model, migrations, data, docs, CI. Read this file before the first edit. For UI work read `DESIGN.md` too.

## Quick path

1. One branch per change, in a worktree under `../ta-web-worktrees/<name>`.
2. Strict TDD: write or adjust the test, watch it fail, then implement.
3. Schema change: generate and commit the migration in the same branch.
4. Run lint, format check, types, unit and integration locally before each push; run E2E and the dev gate suite once, right before opening the PR, not per commit or per fix (see Testing). Report failures verbatim. The pre-commit hook runs Prettier, ESLint and the `gga` review on staged files; do not skip it (`--no-verify`, `LEFTHOOK=0`, `LEFTHOOK_EXCLUDE`) unless the user asks.
5. UI change: screenshots at 1440, 1024 and 390 px, Arcano dark and light (plus any theme the change touches), in `tmp/shots/`, next to the approved mockup.
6. Open the PR: conventional commit title, Spanish body. Leave `openwiki/` alone; a daily task refreshes it (see Wiki). No auto-merge unless asked.

## Strict TDD

1. Write the test (or change the assertion) first. Run it and watch it fail for the right reason.
2. Implement the smallest change that passes.
3. Run the suite the test belongs to, then the push suites (Workflow). E2E waits until the PR is about to open.
4. A refactor PR never edits assertions.

The `localStorage` try/catch rule and the imagery rules (`DESIGN.md`, Imagery) apply to app code. Tests may touch storage directly if they handle the failure with a clear message.

Access control and entitlements are tested at the data layer, in `tests/integration/`: a test calls the Payload local API as an anonymous user, a free member and a premium member, and asserts what each one receives.

## Payload rules

| Rule | Why |
|---|---|
| Every premium collection and field has `access` functions that check the member's entitlement on the server | Gated content must never reach a client that is not entitled |
| Never hide gated content with CSS or client logic | Hidden content still ships in the HTML and the React Server Components payload |
| The local API skips access control unless told otherwise. When rendering for a visitor, pass `overrideAccess: false` and the current `user` | The default (`overrideAccess: true`) is for trusted server jobs only, such as the import |
| Use the local API (`getPayload`) from server code; never call our own REST API from the server | One process, no HTTP round trip, typed results |
| Every schema change ships with a migration (`pnpm migrate:create <name>`, applied with `pnpm migrate`), committed and reviewed. Schema push is for local development only | Production applies migrations; nothing changes the schema by hand |
| Paywalled pages emit Google's paywalled-content structured data | The plan requires it for search |
| Premium themes (Amakna, Bonta, Brâkmar, Ocre) are an entitlement: the server renders a premium `data-theme` only when the member's entitlement allows it, and saving one is rejected otherwise. A theme value from the client, a cookie or `localStorage` is never trusted on its own. Arcano is the free default | Hiding a premium theme behind a client switch would hand it to everyone |
| Premium view modes, such as "Modo compacto" on quest pages, are entitlements like any other: the server picks the layout, and the free view is the full guide | A client-side toggle would hand the feature to everyone |
| Drafts and versions stay on for editorial collections. Live preview turns on for a collection in the same PR as its public page, because it needs that page to render. Quest guides have it: the panel opens `/vista-previa?slug=…`, which needs a Payload session, turns on Next's draft mode and redirects to the guide. The page shows the latest draft only to a request that has both the draft mode cookie and a panel session; the draft mode cookie alone shows the published guide | Torre edits in the panel (plan section 5). A secret in the URL could leak; the session cannot be guessed |
| Achievement pages (`achievement-pages`) and metalogros (`achievement-groups`) are Torre's, with drafts. Each links its DofusDB record (an achievement, or an achievement category) and copies what the page shows: an empty field is filled from DofusDB on save, a written one is never overwritten, and a note under each field says whether the value is DofusDB's or what DofusDB gives (`src/lib/achievements/dofusdb-values.ts`, read through `GET /api/dofusdb-values/:source/:id`). `pnpm data:quests` creates the missing ones as «En preparación» and never changes an existing one. Their `state` (Publicada or En preparación) is Torre's alone; a metalogro's representative, the art of its index tile, is an NPC or a monster | Torre owns the content; DofusDB stays checkable next to it, as with the quest guide summary |
| Derived checklist data is computed in TypeScript at publish time (`src/lib/derive/`), from relationships, not from parsing text | It replaces the old Python pipeline |
| Game data (quests, items, monsters, quest-giver NPCs, achievements and achievement categories from DofusDB) is read-only in the panel and refreshed by a script | Torre picks it through relationship fields. `pnpm data:quests` also imports each NPC's renders, the achievement icons, and the icons of the items and the images of the monsters that a quest, an achievement or a guide shows, into Media once, keyed by `media.gameAsset`, so reruns never duplicate files. Achievements come from the categories under DofusDB's Misiones and Eventos (`QUEST_ROOT_CATEGORIES` in `src/lib/dofusdb/refresh-achievements.ts`), so a new zone or achievement there arrives with the next refresh |

| Rule | Detail |
|---|---|
| Server components by default | `"use client"` only for islands: the checklist app, the header island (menu panels, phone sheet, search dialog), theme switch, member menu, dialogs, and the one island of guide pages (copy, video, image viewer) |
| No client JavaScript on guide pages beyond the shell | The one exception is a single small island, rendered once per page, that copies coordinates, swaps the video link for its player, opens guide images in a fullscreen viewer and opens and closes the rewards bag (`DESIGN.md`, Quest guide components). All four work without it: without JavaScript the bag's list shows open. The live preview island (`LivePreviewRefresh`) renders only in draft mode for a panel user, so visitors never download it. Lighthouse CI enforces the 150 KB budget |
| Fetch data on the server | In server components or route handlers through the local API; no client-side fetching of content. The one exception is the header search index below, which the search dialog fetches when it opens |
| Effects only for external systems | Follow React's [You Might Not Need an Effect](https://react.dev/learn/you-might-not-need-an-effect): derive values during render, handle user actions in event handlers, reset state with `key`, fetch in server components. `useEffect` only syncs with something outside React (DOM listeners, `<dialog>`, browser APIs, the Payload admin form and its API), with a one-line Spanish comment naming that system. ESLint's `react-hooks/set-state-in-effect` (on as `error` through `eslint-config-next`) fails a state copy made in an effect |
| Entitlement checks happen per request on the server | A premium block is not rendered, and not serialized, for a visitor without the entitlement |
| Revalidate on publish | The layout reads the mode cookie, so every page renders per request; what is cached is the data. Guide pages read the published guide through `unstable_cache` with the `guide-pages` tag (`src/lib/guides/cache.ts`), and the `afterChange` and `afterDelete` hooks of `quest-guides`, `media`, `achievement-pages` and `achievement-groups` (a guide shows its achievement page in its breadcrumb and «Misión 2 de 3») call `revalidateTag` with `{ expire: 0 }`, so the next visit reads the new version. Writes made outside the server (the import, `pnpm data:quests`) cannot reach its cache: they show within 10 minutes, the cache's `revalidate`. Pages added later follow the same pattern with their own tag: achievement pages read through `unstable_cache` with the `achievement-pages` tag (`src/lib/achievements/cache.ts`), expired by the hooks of `achievement-pages`, `achievement-groups`, `quest-guides` and `media` |
| Header search index | `GET /api/search/guides` returns every published quest guide as `[title, slug, achievement, level]`, read as an anonymous visitor (`overrideAccess: false`, no user, `draft: false`) by `src/lib/search/guide-index.ts`. It is cached with the `guide-pages` tag like the guide pages, sent with `Cache-Control: public, max-age=300` and gzipped by the endpoint itself, because Next does not compress Payload's API responses (about 95 KB raw and 30 to 36 KB gzipped for 1,272 guides). The first time a search is used (the dialog opens, or the home page's search field gets focus), never on page load, the island loads the search engine with `import()` and fetches the index, one request per page shared by both searches, so neither adds to a page's JavaScript or RSC payload. The guide page sits close to its 150 KB budget (149,716 bytes of script on 2026-11-07): keep search and result code out of the island, and do not import one module from both the island and the lazy chunk, because Turbopack then ships the whole module with the island. The exception is a module small on purpose: `search-query.ts` (the 2-letter check) and the home page's `hero-search-strings.ts` (its ids) ride with the island by design. The home page's island (`HeroSearch`) loads its result rows and the engine the same way, on the field's first focus (`HeroResults.tsx`); the home page sits close to its budget too (about 149,700 bytes of script on 2026-11-07) |
| Guide URLs | A quest guide is `/<slug>` at the root. Achievement pages and metalogros share that slug space: each collection keeps its slug unique, and `rejectSharedSlug` (`src/collections/root-slug.ts`) rejects a slug another of the three already uses. Top-level routes (`/sistema`, `/admin`, `/api`, `/vista-previa`) win over it, so their segments are reserved in `src/lib/guides/slug.ts`: the panel rejects them as slugs and the page returns 404 before querying. A new top-level route adds its segment there |
| Theme and mode | The server renders `data-theme` on `<html>` from the member's saved setting, checked against the entitlement; anyone without it gets `arcano`. The mode (`data-mode`, dark or light) is free: a cookie plus `localStorage`, and an inline `<head>` script sets the mode before first paint (default `dark`), never the theme. The same script sets `data-js` on `<html>`, which the guide's rewards bag needs to start closed; `<html suppressHydrationWarning>` |
| Fonts through `next/font/google` | Montserrat (body and titles) and Lilita One; self-hosted, no layout shift. Montserrat is variable: one latin file holds every weight and it is the only preload; Lilita One loads on demand (`DESIGN.md`, Typography). Do not add a preloaded instance |

## Members and progress

- Anonymous by default: checklists work without an account and save in the browser. Every `localStorage` access is wrapped in `try/catch`.
- One global progress set per member, in our own Postgres tables (Drizzle), not in Payload collections. Quests and quest objectives are keyed by DofusDB quest id, owned items by DofusDB item id, steps by their stable step UUID. Never key progress by step number or position.
- Checklists are views over that set: finishing a quest in one checklist marks it everywhere.
- Each entry carries `updatedAt`; the server merges by latest timestamp; the client queues writes offline and flushes on reconnect.
- Inference rules (prerequisites implied done, completed-by) run once, on the server, over the global set.
- First sign-in offers to import the old keys (`silvestre:*`, `hielos:*`, `global:*`, `dofus-checklists:shared`) and shows what it found before writing anything. The mapping from old step numbers to step UUIDs lives with the import code.
- Members can export and delete their data.

## Media

- Variants are generated once, at upload. Payload's `upload.imageSizes` (`src/lib/media/sizes.ts`) makes AVIF and WebP copies at 480, 800, 1200 and 1600 px wide with sharp, for files uploaded in the panel and by the importer alike, and stores them next to the original (R2 or local disk). A width larger than the original is skipped, except 480, which comes out at the original width. The app never optimizes images on request; no Next image optimization, no Vercel image billing.
- Every media record keeps its alt text, credits, width and height, its generated `sizes` and the original Squarespace URL. `mediaImageAsset` (`src/lib/media/image-asset.ts`) turns a record into the `ImageAsset` that `Picture` and `Figure` render.
- A width or format change only applies to new uploads. `pnpm media:sizes` fills in what older records are missing by re-uploading their originals through Payload. It refuses a remote database without `--remote` and production without `--production`.
- Real game art only (see `DESIGN.md`). Nothing loads from DofusDB or Ankama at runtime.

## Secrets and environment

- `.env.example` lists every variable with an empty or dummy value and a comment. Add a line there in the same change that reads a new variable.

## Wiki

`openwiki/` is the repo's generated documentation, built with the `openwiki` skill. It is the only generated documentation. The hand-written docs it replaced live in `docs/legacy/`, kept for decisions and infrastructure state the code does not show.

- A scheduled agent task outside the repo refreshes the wiki once a day. It is a T3 Code scheduled task on the maintainer's machine. It runs the `openwiki` skill in `update` mode on `main`, opens a docs PR with the `openwiki/` changes and rebase-merges it when `Pruebas` passes. If the skill returns `noop`, there is no PR.
- Feature PRs do not run the skill and do not touch `openwiki/`. If a day has no run, the next run picks up every change since the last update.
- No hook or workflow in the repo runs it. The OpenWiki block below mentions a scheduled GitHub Actions workflow; this repo has none on purpose. If the skill creates `.github/workflows/openwiki-update.yml`, delete it and do not commit it.
- Do not edit generated pages, `openwiki/.claims/`, the indexes or `openwiki/.last-update.json` by hand. Change the source; the next daily run regenerates them.
