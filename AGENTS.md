# Agent contract for ta-web

Rules for any agent that changes this repo. It is the new torrentearcano.com: Torre's Dofus quest guides, achievements, classes, Dofus guides and checklists, with member accounts, per-member progress and premium features. It replaces the Squarespace site and the embeds served from `silvestre-checklist`. The plan, decisions and phases are in `docs/legacy/plan.md`; visual rules are in `DESIGN.md`.

The app skeleton exists: Next.js with Payload, the design tokens, the test suites, the git hooks and CI. Most of the rest is **planned**. When a rule names a path or command that does not exist yet, create it that way. How to run it locally is in the Development section of `README.md`.

## When this applies

Every change: code, content model, migrations, data, docs, CI. Read this file before the first edit. For UI work read `DESIGN.md` too.

## Quick path

1. One branch per change, in a worktree under `../ta-web-worktrees/<name>`.
2. Strict TDD: write or adjust the test, watch it fail, then implement.
3. Schema change: generate and commit the migration in the same branch.
4. Run lint, format check, types, unit, integration and import locally before each push. Locally, E2E runs only the specs that cover what changed (the specs you added or edited, and those for the pages and components you touched), once before opening the PR and again after a fix that touches them; never the full suite. Run the dev gate suite only when the change touches the dev gate (`src/lib/dev-gate/`, `src/proxy.ts`, `robots.txt`, response headers). CI runs every suite on every push to a PR that changes the site, and that run is the full check (see Testing). Report failures verbatim. The pre-commit hook runs Prettier, ESLint and the `gga` review on staged files. The review runs on Sonnet 5.5 (`claude-sonnet-5-5`; `GGA_CLAUDE_MODEL` overrides it), whatever Claude Code's default model is. Do not skip the hook (`--no-verify`, `LEFTHOOK=0`, `LEFTHOOK_EXCLUDE`) unless the user asks.
5. UI change: the layout lint passes (Workflow) and you review your own screenshots at 2560, 1440, 1024, 768 and 390 px (pages use the full width, so a wide screen shows what stretches), Amakna dark and light (plus any theme the change touches), in `tmp/shots/`, next to the approved mockup, before opening the PR.
6. Open the PR: conventional commit title, Spanish body. Leave `openwiki/` alone; a daily task refreshes it (see Wiki). No auto-merge unless asked.

## Stack

| Layer | Choice |
|---|---|
| App | Next.js App Router, TypeScript, React server components |
| CMS | Payload CMS 3, inside the Next app |
| Database | Postgres (Neon); Payload's Postgres adapter; Drizzle for our own tables |
| Members | Better Auth (Google, Discord, magic link; organizations and payments plugins later) |
| Media | Cloudflare R2 through `@payloadcms/storage-s3`, served from a CDN domain |
| Styles | Tailwind v4 with the tokens in `DESIGN.md` |
| Motion | CSS; the Motion library only inside client islands |
| Search | Planned: Postgres full text (`spanish` config plus `unaccent`). Today the header and home searches match titles in a JSON index (`GET /api/search/guides`, see Next rules) |
| Hosting | one long-running Node container (Railway, Fly or a VPS) |

## Strict TDD

1. Write the test (or change the assertion) first. Run it and watch it fail for the right reason.
2. Implement the smallest change that passes.
3. Run the suite the test belongs to, then the push suites (Workflow). E2E waits until the PR is about to open.
4. A refactor PR never edits assertions.

The `localStorage` try/catch rule and the imagery rules (`DESIGN.md`, Imagery) apply to app code. Tests may touch storage directly if they handle the failure with a clear message.

Access control and entitlements are tested at the data layer, in `tests/integration/`: a test calls the Payload local API as an anonymous user, a free member and a premium member, and asserts what each one receives.

## Payload rules

| Rule | Why |
|---|---|
| Every premium collection and field has `access` functions that check the member's entitlement on the server | Gated content must never reach a client that is not entitled |
| Never hide gated content with CSS or client logic | Hidden content still ships in the HTML and the React Server Components payload |
| The local API skips access control unless told otherwise. When rendering for a visitor, pass `overrideAccess: false` and the current `user` | The default (`overrideAccess: true`) is for trusted server jobs only, such as the import |

| Every schema change ships with a migration (`pnpm migrate:create <name>`, applied with `pnpm migrate`), committed and reviewed. Schema push is for local development only | Production applies migrations; nothing changes the schema by hand |

## Redirects

Every Squarespace URL must render or redirect on cutover day (backlog B-03 to B-08). Old URLs that have no page of their own live in one table, `src/lib/redirects/legacy-urls.json`. `src/proxy.ts` looks each request up in a `Map` built once at startup: one lookup per request, no database. A hit answers before Next renders anything, with a redirect straight to the new page or a 410 with a short Spanish page (`src/lib/redirects/gone-page.ts`, no stylesheet, in the visitor's free theme and mode, Amakna dark by default, left aligned like every page, with the system fonts and «Volver a la portada» as the filled primary button). ## Media

- Variants are generated once, at upload. Payload's `upload.imageSizes` (`src/lib/media/sizes.ts`) makes AVIF and WebP copies at 480, 800, 1200 and 1600 px wide with sharp, for files uploaded in the panel and by the importer alike, and stores them next to the original (R2 or local disk). A width larger than the original is skipped, except 480, which comes out at the original width. The app never optimizes images on request; no Next image optimization, no Vercel image billing.
- An animated image (a GIF, WebP or TIFF with more than one frame, such as Torre's spell GIFs on `/yopuka-1`) gets only WebP variants, and they stay animated. sharp's AVIF encoder has no animation: it wrote the frames stacked into one tall strip and failed with `heifsave: image too large` once the strip passed 16384 px. Payload offers no way to skip a size per file, so `patches/payload@3.92.1.patch` (`patchedDependencies` in `pnpm-workspace.yaml`) makes Payload's `createImageSizes` leave the AVIF sizes empty for such a file, in the panel, the importers and on a re-upload alike. When Payload is upgraded, `pnpm install` fails until the patch applies again; redo it with `pnpm patch payload@<version>`, or drop it if Payload fixed this. A single-frame GIF gets AVIF and WebP like any image. The original GIF is what the fullscreen viewer opens.
- Every media record keeps its alt text, credits, width and height, its generated `sizes` and the original Squarespace URL. `mediaImageAsset` (`src/lib/media/image-asset.ts`) turns a record into the `ImageAsset` that `Picture` and `Figure` render.
- A width or format change only applies to new uploads. `pnpm media:sizes` fills in what older records are missing by re-uploading their originals through Payload. It refuses a remote database without `--remote` and production without `--production`. A GIF, WebP or TIFF record that lacks an AVIF variant may be animated, so the script reads its original and counts it complete when it has more than one frame and all its WebP variants (`missingImageSizes` with `animated`, `mayBeAnimated` in `src/lib/media/sizes.ts`); a rerun uploads nothing.
- Real game art only (see `DESIGN.md`). Nothing loads from DofusDB or Ankama at runtime.

## Analytics

Page views go to a self-hosted Umami (backlog S-18), its own Railway service with its own Postgres. No cookies, no personal data, no consent banner (`docs/legacy/plan.md`, Analytics and Consent).

- The tracker is ours, not Umami's `script.js`, which would be one more request and several KB on pages that sit at the edge of the 150 KB budget. `umamiScript` in `src/lib/analytics/umami.ts` is an inline `<head>` script of about 800 bytes, rendered by `src/app/(frontend)/layout.tsx`. It adds no file to the page's JavaScript. It sends `POST {UMAMI_HOST}/api/send` with `{ type: 'event', payload: { website, hostname, language, referrer, screen, title, url } }`, as Umami's own script does, through `fetch` with `keepalive` and `credentials: 'omit'`. It sends once when the page finishes loading and once per App Router route change (`pushState`, `replaceState`, back and forward), 300 ms after the change so the new title is in place. `url` is the path alone, without query or hash, and a change that keeps the path (an anchor, a query, Next's own `replaceState`) is not a new view. A network error is ignored.
- `umamiConfig` decides whether it renders, on every request, from `UMAMI_HOST` (Umami's URL) and `UMAMI_WEBSITE_ID` (the website's UUID in Umami). With either one empty or invalid, or on the dev environment (`isDevEnvironment`), nothing renders and nothing is sent. Changing them needs a restart, not a build. Only production declares them in `.railway/railway.ts`, with `preserve()`.
- E2E and Lighthouse always start the app with both empty (`appWebServers` in `tests/e2e/app-server.ts`, `scripts/lhci-env.ts`). `pnpm test:e2e` starts a second server on the same build and database, on `E2E_ANALYTICS_PORT` (default `E2E_PORT` + 2), with Umami on against `https://umami.e2e.invalid`, which `tests/e2e/analitica.spec.ts` intercepts: no request leaves the machine. The dev gate suite sets both variables and checks that dev sends nothing.
- Owner setup, once: in Umami, Settings, Websites, «Add website» with the production domain; copy its Website ID from the website's edit page; in Railway's production `web` service set `UMAMI_HOST` to Umami's public URL (no trailing slash) and `UMAMI_WEBSITE_ID` to that ID, then redeploy. The repo has no Content Security Policy today; one added later needs Umami's origin in `connect-src`.

## Wiki

`openwiki/` is the repo's generated documentation, built with the `openwiki` skill. It is the only generated documentation. The hand-written docs it replaced live in `docs/legacy/`, kept for decisions and infrastructure state the code does not show.

- A scheduled agent task outside the repo refreshes the wiki once a day. It is a T3 Code scheduled task on the maintainer's machine. It runs the `openwiki` skill in `update` mode on `main`, opens a docs PR with the `openwiki/` changes and rebase-merges it when `Pruebas` passes. If the skill returns `noop`, there is no PR.
- Feature PRs do not run the skill and do not touch `openwiki/`. If a day has no run, the next run picks up every change since the last update.
- No hook or workflow in the repo runs it. The OpenWiki block below mentions a scheduled GitHub Actions workflow; this repo has none on purpose. If the skill creates `.github/workflows/openwiki-update.yml`, delete it and do not commit it.
- Do not edit generated pages, `openwiki/.claims/`, the indexes or `openwiki/.last-update.json` by hand. Change the source; the next daily run regenerates them.
