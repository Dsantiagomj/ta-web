# Agent contract for ta-web

Rules for any agent that changes this repo. It is the new torrentearcano.com: Torre's Dofus quest guides, achievements, classes, Dofus guides and checklists, with member accounts, per-member progress and premium features. It replaces the Squarespace site and the embeds served from `silvestre-checklist`. The plan, decisions and phases are in `docs/legacy/plan.md`; visual rules are in `DESIGN.md`.

The app skeleton exists: Next.js with Payload, the design tokens, the test suites, the git hooks and CI. Most of the rest is **planned**. When a rule names a path or command that does not exist yet, create it that way. How to run it locally is in the Development section of `README.md`.

## When this applies

Every change: code, content model, migrations, data, docs, CI. Read this file before the first edit. For UI work read `DESIGN.md` too.

## Quick path

1. One branch per change, in a worktree under `../ta-web-worktrees/<name>`.
2. Strict TDD: write or adjust the test, watch it fail, then implement.
3. Schema change: generate and commit the migration in the same branch.
4. Run lint, format check, types, unit and integration locally before each push; run E2E and the dev gate suite once, right before opening the PR, not per commit or per fix (see Testing). After the PR is open (review fixes, rebases, conflict resolution), run only the E2E specs that cover what changed, never the full suite or the dev gate; CI runs them all on every push. Report failures verbatim. The pre-commit hook runs Prettier, ESLint and the `gga` review on staged files. The review runs on Sonnet 5.5 (`claude-sonnet-5-5`; `GGA_CLAUDE_MODEL` overrides it), whatever Claude Code's default model is. Do not skip the hook (`--no-verify`, `LEFTHOOK=0`, `LEFTHOOK_EXCLUDE`) unless the user asks.
5. UI change: screenshots at 1440, 1024 and 390 px, Arcano dark and light (plus any theme the change touches), in `tmp/shots/`, next to the approved mockup.
6. Open the PR: conventional commit title, Spanish body. Leave `openwiki/` alone; a daily task refreshes it (see Wiki). No auto-merge unless asked.

## Strict TDD

1. Write the test (or change the assertion) first. Run it and watch it fail for the right reason.
2. Implement the smallest change that passes.
3. Run the suite the test belongs to, then the push suites (Workflow). E2E waits until the PR is about to open.
4. A refactor PR never edits assertions.

The `localStorage` try/catch rule and the imagery rules (`DESIGN.md`, Imagery) apply to app code. Tests may touch storage directly if they handle the failure with a clear message.

Access control and entitlements are tested at the data layer, in `tests/integration/`: a test calls the Payload local API as an anonymous user, a free member and a premium member, and asserts what each one receives.

CI (`.github/workflows/ci.yml`) runs lint, types, unit, integration, build, E2E, the dev gate suite, the budgets and the dependency audit (`docs/legacy/security.md`). The repo is private, so Actions minutes are limited: keep jobs cached and skip what a change cannot affect. The `Cambios` job decides what runs from the PR's files (`git diff --no-renames`, so a moved file counts by its old path too; `scripts/ci/ci-scope.ts`, tested in `tests/unit/ci-scope.test.ts`); the highest level among the files wins. The audit runs on every PR, since a new critical advisory blocks them all:

| Files | Jobs |
|---|---|
| Docs only: `*.md` outside `src/` and `public/`, `docs/**`, `openwiki/**` | lint, format and audit |
| Nothing the site, E2E or budgets load: `scripts/import/**`, `scripts/hooks/**`, the one-off scripts listed in `ci-scope.ts`, `tests/unit/**`, `tests/integration/**`, `tests/fixtures/**`, tool config | plus types, unit and integration |
| Anything else, including `src/**`, `package.json`, `pnpm-lock.yaml`, `.github/**`, `tests/e2e/**`, an unknown or new path, and every push to `main` | all |

A new script under `scripts/` runs everything until it is added to the list in `ci-scope.ts`; add it only if nothing in `src/`, `scripts/seed-e2e.ts`, `scripts/lhci.ts` or `tests/e2e/app-server.ts` imports it. `Pruebas` is the one required check: it passes when every job `Cambios` asked for passed, and fails when one of them was skipped, or when any job failed or was cancelled. Only the Build job saves the `.next` cache; E2E and the budgets build with another environment and only restore it. The budgets run in parallel with E2E as two jobs, each building on its own Postgres, and measuring part of the pages of `lighthouserc.cjs` (`LHCI_SHARD=1/2` and `2/2`: contiguous, sizes differ by at most one, the first part takes the extra page); each uploads its reports as the `lighthouse-1` or `lighthouse-2` artifact (7 days). Import joins when it exists. The AI review (`gga`) runs only in the pre-commit hook, not in CI.

| Rule | Detail |
|---|---|
| Service config lives in `.railway/railway.ts` | Railway's infrastructure as code. Railway retired `railway.json` for new services. Change it with a unit test in `tests/unit/railway-config.test.ts`, then `railway config plan` and `railway config apply` per environment |

| Dev deploys `main` on its own | Railway's GitHub integration deploys every push to `main` without waiting for the GitHub checks (`checkSuites: false`): each PR already passed the same CI before its rebase merge. The dev smoke runs after the deploy |

## Payload rules

| Rule | Why |
|---|---|
| Every premium collection and field has `access` functions that check the member's entitlement on the server | Gated content must never reach a client that is not entitled |
| Never hide gated content with CSS or client logic | Hidden content still ships in the HTML and the React Server Components payload |
| The local API skips access control unless told otherwise. When rendering for a visitor, pass `overrideAccess: false` and the current `user` | The default (`overrideAccess: true`) is for trusted server jobs only, such as the import |
| Use the local API (`getPayload`) from server code; never call our own REST API from the server | One process, no HTTP round trip, typed results |
| Every schema change ships with a migration (`pnpm migrate:create <name>`, applied with `pnpm migrate`), committed and reviewed. Schema push is for local development only | Production applies migrations; nothing changes the schema by hand |
| Paywalled pages emit Google's paywalled-content structured data | The plan requires it for search |
| Premium themes (Amakna, Bonta, Brâkmar, Ocre) are an entitlement: the server renders a premium `data-theme` only when the member's entitlement allows it, and saving one is rejected otherwise. A theme value from the client, a cookie or `localStorage` is never trusted on its own. Arcano is the free default | Hiding a premium theme behind a client switch would hand it to everyone |
| Premium view modes, such as "Modo compacto" on quest pages, are entitlements like any other: the server picks the layout, and the free view is the full guide | A client-side toggle would hand the feature to everyone |
| Drafts and versions stay on for editorial collections. Live preview turns on for a collection in the same PR as its public page, because it needs that page to render. Quest guides, achievement pages, Dofus guides and checklists have it: the panel opens `/vista-previa?slug=…`, which needs a Payload session, turns on Next's draft mode and redirects to the guide. The page shows the latest draft only to a request that has both the draft mode cookie and a panel session; the draft mode cookie alone shows the published guide | Torre edits in the panel (plan section 5). A secret in the URL could leak; the session cannot be guessed |
| Dofus guides (`dofus-guides`) are Torre's, with drafts: one per Dofus, linked to its DofusDB item (the egg comes from it), with his order, level, tag (Primordial, Evento or none), glow color, other names for search, Prerrequisitos, Necesitarás in groups of rows (a game item with its quantity, or a note), the achievements and quests in order (an achievement block links its achievement page, whose quests the page shows, so they are edited in one place; a metalogro block groups several; quest blocks link quest guides with Torre's note), an optional step-by-step body with the quest guide blocks, a YouTube video and a checklist link. Their `state` (Publicada or En preparación) is Torre's alone. `pnpm import:dofus-guides` seeds them from his pages: it creates what is missing and, when rerun, only rewrites a field that still holds what the last import wrote (`importSnapshot`, hidden in the panel), so it never undoes an edit made in the panel. It brings the Dofus items and the Necesitarás items DofusDB has with their icons, the step screenshots and the YouTube poster (`videoPoster`) into Media, and lists the achievements, quests and items it could not match and the achievements whose quest list differs from their achievement page | Torre owns the content; the quests of each achievement live on its achievement page only |
| Achievement pages (`achievement-pages`) and metalogros (`achievement-groups`) are Torre's, with drafts. Each links its DofusDB record (an achievement, or an achievement category) and copies what the page shows: an empty field is filled from DofusDB on save, a written one is never overwritten, and a note under each field says whether the value is DofusDB's or what DofusDB gives (`src/lib/achievements/dofusdb-values.ts`, read through `GET /api/dofusdb-values/:source/:id`). `pnpm data:quests` creates the missing ones as «En preparación» and never changes an existing one. Their `state` (Publicada or En preparación) is Torre's alone; a metalogro's representative, the art of its index tile, is an NPC or a monster. An achievement page's `intro` and `outro` are Torre's rich text, whose editor also takes a YouTube «Vídeo» block (`ProseVideoBlock`, rendered as the video facade). `pnpm import:achievement-prose` fills them from his Squarespace pages with the `importSnapshot` rule of the Dofus guides (hidden in the panel): it writes a field only while it is empty or still holds what the last import wrote, so a second run changes nothing and an edit made in the panel stays. It decides each field before uploading anything, so a kept field uploads nothing; a screenshot or poster that fails to download is reported and skipped, while any other error stops the run | Torre owns the content; DofusDB stays checkable next to it, as with the quest guide summary |
| Checklists (`checklists`) are Torre's, with drafts and a `state` (Publicada or En preparación; while En preparación, `legacyHref` links the Squarespace checklist and `/<slug>` redirects a visitor there). Each step keeps a `stepId`, a UUID made once by the collection's `beforeValidate` hook (`src/lib/checklists/step-ids.ts`) and kept through edits, reorders, drafts and reimports; a duplicated row gets a new one, and the collection cannot be duplicated. A step's text is a list of segments: «Detente aquí» needs a quest and an objective index valid for that quest's stored stages; «Aquí se resuelve» lists the stepIds it closes, all in the same checklist (`src/collections/checklist-rules.ts`). Each step also keeps its `zone`, Torre's grouping in the step list («Anutropía»), which is not always where its quests start. A «Necesitarás» row is a game item or, when it is not one (kamas, a spell), a text `label`, with its group and whether it counts in the totals: the import never drops a row. There is no effort field and no stored weight: the progress weights are computed | Progress is keyed by `stepId`; weights come from quest data |
| Derived checklist data is computed in TypeScript at publish time (`src/lib/derive/`), from relationships, not from parsing text | It replaces the old Python pipeline |
| Game data (quests, items, monsters, the NPCs that give a quest or that a quest objective names, subareas with their area, achievements and achievement categories, and dungeons with their bosses, from DofusDB) is read-only in the panel and refreshed by a script | Torre picks it through relationship fields. A quest objective keeps only `subAreaId`; its name and area come from `subareas`, by `dofusId`. `pnpm data:quests` also imports each NPC's renders, the achievement icons, and the icons of the items and the images of the monsters that a quest, an achievement or a guide shows, plus every dungeon boss, into Media once, keyed by `media.gameAsset`, so reruns never duplicate files. Achievements come from the categories under DofusDB's Misiones and Eventos (`QUEST_ROOT_CATEGORIES` in `src/lib/dofusdb/refresh-achievements.ts`), so a new zone or achievement there arrives with the next refresh. It ends by listing the dungeon rows of published achievement pages that show the generic dungeon icon in «Necesitarás en total»: no single dungeon matched, or its boss has no image (`DESIGN.md`, Achievement page components). Torre fixes one by picking the dungeon in the quest guide that has the note (`summary.needs.dungeons`, «Mazmorras de las notas»): the pick wins over the match by name, and the report counts the rows a pick resolved |

## Redirects

Every Squarespace URL must render or redirect on cutover day (backlog B-03 to B-08). Old URLs that have no page of their own live in one table, `src/lib/redirects/legacy-urls.json`. `src/proxy.ts` looks each request up in a `Map` built once at startup: one lookup per request, no database. A hit answers before Next renders anything, with a redirect straight to the new page or a 410 with a short Spanish page (`src/lib/redirects/gone-page.ts`, no stylesheet). The `Location` uses the public origin, `NEXT_PUBLIC_SITE_URL` (`src/lib/site/origin.ts`), because behind Railway's proxy the request only knows the internal host. Paths match lowercased and without a trailing slash, and the old query string is dropped.

| Rule | Detail |
|---|---|
| One section per source | Each top-level key is a section with a `description` (the backlog item and who keeps it), `moved` (old path to new path, with an anchor if needed), `gone` (410) and an optional `permanent`. Today: `hubs` (B-06), `metalogros` (B-05) and `stubs` (B-04) |
| 301 for what is stable, 307 for what still changes | `moved` answers 301, which browsers and crawlers keep for good. A section that a script still rewrites sets `permanent: false` and answers 307. `stubs` does until cutover day, when `pnpm redirects:stubs --cutover` drops the flag and its redirects become 301 |
| 410 only for what is gone for good | A URL whose page will exist later gets no row, so it answers 404 until the page is published |
| Porting a section adds its URLs | When a Squarespace section is ported (B-08), add a section named after it with the old URLs whose slug changes, and a 301 for each. A URL whose slug stays the same needs no entry: the new page answers it |
| No chains, no open redirects | `src/lib/redirects/table.ts` refuses a URL in two sections, a target that is itself in the table, a target that leaves the site (`//`, a backslash, whitespace), a source that is not a flat slug, and a reserved route (`RESERVED_SLUGS`). `tests/unit/redirect-table.test.ts` runs it on the real file and is the gate. At runtime a bad table is logged and the proxy runs with no redirects, so one bad row never takes the site or `/api/health` down |
| No shadowing | The root-slug hook (`src/collections/root-slug.ts`) rejects a guide, achievement page, Dofus guide or checklist whose slug is in the table, and tells Torre to have the row removed; slug autofill skips those slugs. Metalogros are exempt: their slug is the anchor of their panel, not a page. `/sitemap.xml` never lists a table source |
| Do not redirect what is still on Squarespace | Pages not ported yet (classes, dungeons, legal pages, tools, `/subscribe`) stay out of the table until their section is ported or Torre drops them |
| `stubs` is generated | `pnpm redirects:stubs` reads the public API of a deployed site (dev by default, `--from <origin>` for production), maps each of the 166 empty stubs to the achievement page of its achievement or quest (`scripts/redirects/stub-map.ts`), and rewrites only that section. A stub redirects only when its page is published. While that page is «En preparación» the stub has no row (404); with no page to wait for, it gets a 410. A name that matches several achievements is left out and reported, for `STUB_OVERRIDES`. It prints what went where. Rerun it after Torre publishes achievement pages, and against production with `--cutover` on cutover day |

`/sitemap.xml` (`src/app/sitemap.ts`) lists the home page, the three indexes and every published quest guide, achievement page, Dofus guide and checklist in the Publicada state, with `lastModified`; an index's date is the latest of what it lists, «En preparación» entries included, since they show. It reads as an anonymous visitor through `unstable_cache` with the `guide-pages`, `achievement-pages`, `dofus-guides` and `checklists` tags. The production `robots.txt` points to it.

## Members and progress

- Anonymous by default: checklists work without an account and save in the browser. Every `localStorage` access is wrapped in `try/catch`.
- In the browser, all checklists share one key, `ta-web:progress` (`src/lib/checklists/progress/`). On a checklist page, old `silvestre-checklist` keys still in the browser are merged into it once per old checklist (`migrated`), by union, never deleting or changing the old keys. The migration code loads with `import()` only when such keys exist. Members are not built yet: the sign-in import below is still planned.
- One global progress set per member, in our own Postgres tables (Drizzle), not in Payload collections. Quests and quest objectives are keyed by DofusDB quest id, owned items by DofusDB item id, steps by their stable step UUID. Never key progress by step number or position.
- Checklists are views over that set: finishing a quest in one checklist marks it everywhere.
- Each entry carries `updatedAt`; the server merges by latest timestamp; the client queues writes offline and flushes on reconnect.
- Inference rules (prerequisites implied done, completed-by) run once, on the server, over the global set.
- First sign-in offers to import the old keys (`silvestre:*`, `hielos:*`, `global:*`, `dofus-checklists:shared`) and shows what it found before writing anything. The mapping from old step numbers to step UUIDs lives with the import code.
- Members can export and delete their data.

## Media

- Variants are generated once, at upload. Payload's `upload.imageSizes` (`src/lib/media/sizes.ts`) makes AVIF and WebP copies at 480, 800, 1200 and 1600 px wide with sharp, for files uploaded in the panel and by the importer alike, and stores them next to the original (R2 or local disk). A width larger than the original is skipped, except 480, which comes out at the original width. The app never optimizes images on request; no Next image optimization, no Vercel image billing.
- Every media record keeps its alt text, credits, width and height, its generated `sizes` and the original Squarespace URL. `mediaImageAsset` (`src/lib/media/image-asset.ts`) turns a record into the `ImageAsset` that `Picture` and `Figure` render.
- A width or format change only applies to new uploads. `pnpm media:sizes` fills in what older records are missing by re-uploading their originals through Payload. It refuses a remote database without `--remote` and production without `--production`.
- Real game art only (see `DESIGN.md`). Nothing loads from DofusDB or Ankama at runtime.
